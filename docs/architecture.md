# Architecture

The backend uses synchronous FastAPI route functions, Pydantic input/output schemas, SQLAlchemy 2 ORM models, and one SQLite file. The frontend is a separate Next.js App Router project with a dark dashboard (`/`) and oshi management (`/oshi`), connected through a typed browser API client. The backend contract is unchanged by frontend integration.

## Request and data lifecycle

`create_app(database_path)` constructs an app and its engine. The lifespan handler creates missing tables and inserts missing local discovery metadata on startup, then disposes the engine on shutdown. Startup never seeds tracked Oshi or updates. Constructing or importing the app does not create a database. Each request opens one SQLAlchemy session; a successful mutation commits once, and uncommitted work rolls back when the session closes.

Route modules access the ORM directly. Scoring is a pure function in `app/scoring.py`.
The manual ingestion package calls source adapters and writes ordinary Updates directly
through the ORM; it runs independently of the web servers. There is no repository layer,
background worker, scheduler, or network call in API/seed logic. See [ingestion.md](ingestion.md).

SQLite uses Python 3.12's explicit transactional mode (`autocommit=False`). Foreign-key enforcement is enabled on every connection, temporarily outside a transaction. This follows the [SQLAlchemy SQLite transaction and foreign-key guidance](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html). Connections allow FastAPI's worker threads, while sessions stay scoped to a single request, following the [FastAPI session-per-request pattern](https://fastapi.tiangolo.com/tutorial/sql-databases/).

## Model decisions

| Concern | v0.1 decision |
| --- | --- |
| IDs | Integer primary keys; association table has composite `(update_id, oshi_id)` primary key. |
| Oshi identity | Names are not unique; a character/title/person can share a display name. |
| Priority | Integer 0–100, default 50; larger values sort first. Does not multiply relevance points. |
| Active state | Default `true`; inactive oshi remain stored and filterable but contribute no followed/keyword points. |
| Keywords | Managed inside oshi create/patch. Integer weight 0–100, default 1; positive weights enable the fixed keyword bonus. |
| Keyword replacement | Supplied array replaces the whole set; omitted array preserves it; `[]` clears it. Exact-value matches retain IDs. Unicode/case-equivalent duplicates within one oshi are rejected. |
| Associations | API updates accept explicit `oshi_ids`; unknown or duplicate IDs are rejected. Manual ingestion separately matches active tracked identities before creating associations. |
| Deletion | Delete oshi, its keywords, and join rows; retain update history and other oshi. Recalculate affected scores in the same transaction. |
| Timestamps | `created_at` is generated by the server. `published_at` and `deadline` are nullable, timezone-aware input; storage is UTC and responses include `Z`. |
| Event dates | Nullable calendar `start_date` / `end_date`. If both exist, end must be on/after start; PATCH validates the merged record. |
| Source URLs | Required HTTP(S) URLs, never fetched; URLs may repeat across distinct updates. |
| Relevance | Read-only API field, computed at create/content patch and after linked oshi edits/deletion. |
| Status | Default `NEW`; any requested enum status may change directly to any other. |
| Stats | Global totals and counts for every category/status, including zero buckets. |

Enums, score/weight/priority ranges, date ordering, foreign keys, and duplicate join rows have database constraints in addition to API validation. Important filtering and foreign-key columns are indexed.

## Discovery catalog

`CatalogEntity` and `EntityAlias` hold discoverable metadata separately from personal `Oshi`. Catalog types reuse `OshiType`; ITZY uses `ARTIST`, with its group identity in the description. Eight local entities and seventeen aliases are inserted idempotently by `app/catalog.py` on startup. Unique `(provider, external_id)` and `(entity_id, normalized_alias)` keys make repeat startup safe and preserve existing metadata edits. Local external IDs are stable seed slugs, not identifiers fetched from a provider. No news/update records are created by catalog seeding.

`CatalogTracking` is a small optional link table with unique entity and Oshi IDs. It keeps discovery identity through a personal rename without adding a column to the existing Oshi table. Deleting an Oshi cascades only to its link, keywords, and update associations; it never deletes the catalog entity or aliases. Catalog deletion would likewise remove only the link, not personal Oshi. Manual creation remains independent. Existing rows are recognized by same-type normalized canonical/alias name matching, without changing or backfilling personal rows at startup.

Discovery uses a direct in-memory scan of the small local catalog, loaded with its aliases. Python NFKC/casefold/whitespace normalization avoids SQLite's limited Unicode case handling. Exact names rank ahead of exact aliases, then prefixes and substrings. Result size is capped. There is no full-text engine, provider framework, recommendation service, or external network access.

Tracking first reserves SQLite's write lock using a no-op update of the target catalog ID, before reading existing tracking state. The transaction then returns an existing Oshi or creates one and its unique catalog link together. This prevents concurrent discovery Add requests from creating duplicate personal rows while keeping the existing manual-create contract unchanged. Keywords copy the canonical name and useful aliases at weight 1; existing personal keyword/priority/active values are left alone.

## Local operation

Scripts bind the backend and frontend to `127.0.0.1`. Next.js telemetry is disabled in its npm scripts. The backend allows only localhost Host headers and CORS origins `http://localhost:3000` / `http://127.0.0.1:3000`. CORS is browser integration configuration; it is not authentication. The project intentionally has no authentication and must stay on loopback.

The optional local CLI in `scripts/oshi.py` wraps these existing launch commands. A detached Python supervisor anchors each service process group; `.runtime/` holds atomic ownership state and append-only logs. Commands serialize through a file lock, validate process identity and HTTP readiness, and terminate only verified owned groups. The installer creates a quoted wrapper in a user-owned PATH directory. It changes neither application contracts nor shell startup files. See [local-cli.md](local-cli.md) for shutdown, test isolation, and recovery decisions.

The default SQLite path is absolute after resolving `data/oshi.db` relative to this repository. `OSHI_DATABASE_PATH` overrides the filesystem path. No database URL abstraction is needed for this SQLite-only milestone.

Swagger UI at `/docs` and ReDoc at `/redoc` are FastAPI's standard documentation pages and load their UI assets from CDNs. Dashboard data requests go only to the configured local API. Figma marker assets are stored locally and typography uses a system font stack. Source links open the stored URL only when clicked. `/openapi.json` is available locally without documentation UI assets.

## Schema changes and dependency management

`Base.metadata.create_all()` initializes missing tables. It does **not** alter existing tables. The discovery milestone adds only `catalog_entities`, `entity_aliases`, and `catalog_tracking`; no original table is renamed, repurposed, or altered. A SQLite backup is taken before applying those additions, and old-schema startup is covered by tests. There is no migration framework yet. A future change to existing columns requires an explicit migration with a backup path; never erase personal data.

The ingestion foundation adds only `source_states` and `ingested_records`, preserving all
seven prior tables. Per-source batches commit provenance, new Updates, associations,
scores, and success state together. SQLite's writer is reserved before dedupe reads;
network calls happen before that transaction. Failed batches roll back and record failure
state separately. Dry-run executes against a disposable SQLite snapshot, including when
the personal database predates ingestion. The public API is unchanged.

`backend/pyproject.toml` declares compatible dependencies; `backend/requirements-dev.lock` records tested exact runtime/development/build versions. `scripts/setup.sh` installs the lock and then the local package without dependency resolution or build isolation. `frontend/package-lock.json` is installed with `npm ci`. TypeScript ESLint is pinned to 8.46.4 to keep lint tooling compatible with the installed Node 22.11 and the Next.js minimum. Tests use HTTPX2 for the current Starlette TestClient; one upstream AnyIO alias deprecation is narrowly ignored, while other warnings fail tests.

After an intentional Python dependency upgrade, regenerate the lock from a clean development venv (including setuptools and wheel):

```sh
backend/.venv/bin/python -m pip freeze --all --exclude pip --exclude oshi-dashboard-backend > backend/requirements-dev.lock
```

Then rerun the relevant checks. The lock targets local development on Python 3.12+; it is not a deployment artifact.

## Seed semantics

Seeding is explicit and transactional. Oshi are found by exact name/type; updates by stable demo source URL. Missing rows are inserted; existing content, keywords, scores, statuses, and dates are left alone. Initial demo dates are relative to the UTC date of the first seed. Subsequent seeding does not advance them. Deleting or changing fixture identity fields can cause a later seed to recreate those fixtures, so seed is a development utility, not a synchronization system.

Tests use an app factory and temporary on-disk SQLite databases. They exercise the same connection settings, foreign keys, request validation, and transaction behavior used locally.

## Frontend integration

The root layout preserves `AppShell` and its oshi/stats context across route changes. Client components use ordinary React state and hooks. Filters live in the URL and use the stable API query names; free-text search stays in React state and searches only loaded data. `lib/api.ts` owns HTTP calls, timeout/cancellation, typed responses, and error messages. There is no frontend state library, UI framework, or Next.js proxy backend.

Status/oshi changes wait for successful API responses before refetching affected lists, stats, and detail data. Late responses to obsolete filter/detail requests are discarded. Native HTML dialogs provide focus containment and Escape dismissal. See [frontend integration](frontend-integration.md) for pagination, keyword-context limits, configuration, and verification.
